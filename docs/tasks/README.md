# 任务目录约定

一需求一文件；索引即目录，本文件不列具体任务。

## 两级目录

- 仓库级任务：`docs/tasks/active/`（在办）、`docs/tasks/done/`（已结项）。
- 单插件任务：`plugins/<插件名>/docs/tasks/active/`、`plugins/<插件名>/docs/tasks/done/`，结构相同。
- 目录不存在时按需创建；空目录用 `.gitkeep` 占位。

## 命名

`<YYYY-MM-DD>-<slug>.md`，slug 与分支名一致：

- `feature/todo-fragment` → `2026-10-20-todo-fragment.md`
- `hotfix/login-timeout` → `2026-10-20-login-timeout.md`

分支名唯一，所以文件名唯一；并行分支各加各的文件，合回零冲突。

## 生命周期

1. 计划阶段新建 `active/<id>.md`，内容按下方模板。
2. 实施中只由该任务的 owner 修改，其他人不改。
3. 结项时 `git mv active/<id>.md done/<id>.md`，内容保留。
4. 状态由目录表达，不在文件里写状态字段；不手工维护任务清单。

## 任务文件模板

段落顺序固定：

1. 目标（spec）：要解决什么；边界（明确不做什么）。
2. 验收标准：每条可判定——一条命令，或一个可观察行为。
3. 澄清结论：用户已定的取舍。
4. 方案（plan）：机制依据（已核实的事实 + 来源）、影响文件清单、风险。
5. 任务（tasks）：可勾选的实施步骤。
6. 结果（review）：改动文件清单、验证方式与结果（命令 + 结论）、遗留问题。

## 并行纪律

- 只新建/修改自己名下的任务文件，不碰别人的。
- 不手工合并任务清单；合并分支时任务文件天然不冲突。
- 同一需求拆给多个 worker 时，先把「目标 + 验收标准」合入集成分支，再开实现分支。

## 分工

为什么这么选 → 决策笔记；被纠正的错误 → lessons；当前行为 → 代码与文档。
