# 0002 会话标题按 `MMDD｜类型｜主题` 生成

- 时间：2026-09-28
- 状态：实施（implemented）
- 关联：`plugins/session-title-rule/`

## 背景

DSH 的会话标题默认取首条用户消息的前 5 个词（`fallbackSessionTitle`，40 字节）。左侧栏里一长串「写一个插件，会话生成的标题按以下规则生成…」既看不出类型也看不出主题。

用户给了一套命名规则：`MMDD｜类型｜主题`，类型八选一，主题一句话提炼实际内容且不重复项目名，并提供了一批边界（判断不出就保留原名、已归档不改、非主对话不改）。

那套规则的原始语境（`session` 表 / `tasks` 表 / `archived=1` / `selection_side_chat` / Claude-Mem）不是 DSH 的概念，需要逐条映射到 DSH 的等价物，映射不上的要显式说明而不是硬凑。

## 决策

1. **只替换标题 provider，不动客户端。** 注册 `ctx.sessionTitle` 的唯一 provider（`automatic: 'first-prompt'`），标题由服务写进会话日志并投影到左侧栏，浏览器侧零改动。
2. **`MMDD` 由插件计算，模型只产出「类型｜主题」。** 时间取 `session.header.createdAt`（对应规则书的 `time_created`），加 UTC+8 固定偏移后取 UTC 字段，因此与机器本地时区无关。**不读 `updatedAt`。**
3. **patch 层禁用内置的 `session-title-llm` 行。** `sessionTitle.register()` 全局只接受一个 provider，已注册即抛错；不禁用会让本插件的 fiber 直接失败。
4. **「判断不出主题 → 保留原名」落地为 provider 抛错。** 服务会吞掉 provider 异常并保留它自己落的 fallback 标题。DSH 的 provider 契约要求返回非空标题，没有第二种表达方式。
5. **零 `@deepseek-ai/*` 依赖。** 只用 `ctx` 服务，消息按完整 Message 形状（id + role + content + source）构造，与内置 provider 逐字一致。
6. **加载时补跑一次。** `first-prompt` 只在首条消息那一刻调度，已有会话的消息早就过去了；`sessions.list()` 遍历 + `sessionTitle.refresh()` 让当前会话立即拿到标题。
7. **缺失概念的显式处理**：`tasks` 表不适用；observer/Claude-Mem 无对应物不实现；`selection_side_chat` 用 `header.parentSession` / `origin: 'subagent'` 表达。

## 理由

- **为什么不让模型算日期**：日期算术是不可靠的一环，且一旦算错会产生一个看起来「格式正确」的错误标题，无法自动发现。拆出来后 `MMDD` 的正确性完全由单元测试覆盖。
- **为什么 provider 抛错等于保留原名**：读 `session-title/src/index.ts:568-573` 与 `:798-832`——服务在调用 provider 之前会先落一个 fallback 标题，provider 抛错只是 warn，标题留在 fallback 上。这正好是「保留原名，禁止猜测」。
- **为什么必须自己算字节预算**：`normalizeSessionTitle(title, this.config.maxTitleBytes)` 对超长标题是**截断**而非报错（`normalize.ts:39-51`），标题被悄悄剪掉不会有任何提示。`MMDD｜类型｜` 固定占 16 字节，主题裁到 20 汉字后总长 76 字节，留在 80 以里。
- **为什么零依赖**：实测从插件目录 `require.resolve('@deepseek-ai/dsh-llm')` 返回 `MODULE_NOT_FOUND`——插件被 `link:` 到 profile 后，Node 从插件真实路径解析，够不到 profile 的 `node_modules`。服务调用不需要这些类型，形状假设改用契约测试对照权威源兜住。
- **为什么不写 `export default`**：一旦有默认导出，`unwrapExports` 会取默认导出、丢掉整个 ESM 命名空间，`inject`/`name` 静默消失（事故 0001）。契约测试直接断言 `host.default === undefined`。

## 替代方案

| 方案 | 为什么放弃 |
| --- | --- |
| `automatic: 'all-prompts'`（每轮重新生成） | 用户明确选择首条消息后生成一次。all-prompts 会在每轮多一次模型调用，且标题在会话进行中反复变化 |
| 客户端半区自己渲染/改写标题 | 标题的真相在会话日志（`session/title` 事件）与服务端投影里；客户端改写会与持久化状态分裂 |
| 直接 import `@deepseek-ai/dsh-session-title` 复用 `SessionTitleProviderId` 等类型 | 插件目录解析不到这些包。类型只在编译期有用，服务调用不依赖它们 |
| 用 `RequestUserInput`（只带 role/content）构造消息 | 该形状只存在于较新的 DSH 版本（源码 checkout 与已安装产物都没有）。完整 Message 两版都接受 |
| 插件自己实现「批量重命名历史会话」的工具/命令 | 用户要的是「会话生成的标题」；补跑只覆盖进程内活跃会话，够用且不需要新交互面 |
| 硬编码「不重复项目名」以外的项目识别方式 | `header.cwd` 是唯一可靠来源，写进提示词即可 |

## 影响

- **接管范围**：本插件使内置的 `session-title-first-prompt-llm` 在整个 profile 内失效（它被禁用）。卸载本插件不会自动恢复该行——profile 的 `cordis.patch.yml` 由 plugin-manager 维护，移除 bundle 时同步移除禁用。
- **每会话一次模型调用**：首条消息后发起，`maxTokens: 64`、30s 超时、`purpose: 'session-title'`。补跑时对每个活跃会话各一次。
- **标题上限**：`maxTitleBytes: 80`。若 profile 调小该值，需同步调小 `src/rule.js` 的 `MAX_TITLE_BYTES`；契约测试会先失败。
- **契约测试锚点**：锚定 DSH 源码 checkout（`DSH_SOURCE`），而运行中的 DSH 可能更新（本次调研就发现运行版本有源码 checkout 里没有的 `RequestUserInput`）。源码不在时相关用例跳过；运行版本的差异只能靠端到端验证发现。
- **空壳客户端半区**：`client.js` 不注册任何行为，仅为满足仓库门禁的统一形状。若将来需要展示生成状态，半区已就位。
