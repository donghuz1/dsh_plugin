# 标题辅助调用显式选择最低推理档

状态：implemented
类别：bug-fix
日期：2026-10-19
插件：session-title-rule

## 背景

DSH `0.2.1-rc.2` 起，LLM 适配器在调用方省略 `reasoningEffort` 时使用连接默认值（本机 profile 的主请求是 `max`）。本插件的辅助标题调用只给 64 个输出 token，且没有传推理档：推理 token 先耗尽预算，流以 `finish: max-tokens` 结束且没有任何文本，provider 按约定抛错，`sessionTitle` 服务保留 fallback 标题。表现是「新版本后标题不再生成」，而 provider 契约本身没有变化（补跑 `refresh()` 仍能成功）。

内置标题 provider 的参考实现在 `prepareCall` 里用 `selectReasoningEffort = model.reasoning?.efforts[0]?.id` 显式选最低档，本插件此前漏了这一步。

## 决策

辅助调用改成两段式，并显式选档：

1. `ctx.llm.resolveModelInfo(provider, model, signal)` 读 `reasoning.efforts`，取第一档（适配器偏好顺序的最低档）。
2. `ctx.llm.prepareCall({ ...route, maxTokens, reasoningEffort }, signal)`，再用 `prepared.stream({ ...prepared.config, messages, system, sessionId, purpose, signal })` 派发。
3. 查询失败、或模型不暴露推理能力时不传 `reasoningEffort`，交给适配器默认值（保证旧运行时与不支持推理的模型不因新字段失败）。

辅助消息同时改为无身份的 `RequestUserInput`（`{ role: 'user', content }`）：请求不落会话日志，不需要伪造 `Message` id 与 source kind。

## 理由

- `efforts` 是「适配器偏好顺序」，第一档最低；显式选它后输出 token 全部用于标题文本，实测同一条提示词从 `max-tokens`+空文本变为 `stop`+14 字。
- `prepareCall` 把能力解析与派发绑定到同一次适配器注册，并返回补齐默认值、深冻结的 `config`；`prepared.stream()` 要求调用方的 call-config 与它逐字段一致，正好避免「解析一次、派发另一次」的代际漂移。
- 两步式（先 `resolveModelInfo` 再 `prepareCall`）不依赖 `0.2.x` 新增的 `prepareCall` 第三参 `configure`，源码 checkout（0.1.7）与运行版本（0.2.1）都能工作。

## 替代方案

| 方案 | 放弃原因 |
| --- | --- |
| 把 `maxTokens` 从 64 提到 256/512 | 只是抬高天花板；`max` 档推理仍可能吃光，且每次标题都多付延迟与成本。 |
| 硬编码 `reasoningEffort: 'off'` | 不是所有模型都暴露 `off`；适配器会抛 `UNSUPPORTED_REASONING_EFFORT`，把可恢复的失败变成永久失败。 |
| 接受 `max-tokens` 终止帧，只要有文本就解析 | 实测 `max` 档下通常没有文本；即便有也是被截断的输出，会把不完整标题当成功。 |
| 复制内置 provider 的完整实现（含 `session/title-llm-request` 记录） | 插件零 import 拿不到 `dsh-session-title-llm` 的共享 helper；记录辅助请求不是本插件的职责。 |

## 影响

- 自动命名路径恢复；补跑路径不变。
- 已存在的 `fallback` 会话会在下次插件加载（重启 Desktop）时由补跑改成规则标题，每个会话一次模型调用。
- 契约测试新增 `RequestUserInput`、`resolveModelInfo` / `prepareCall`、`reasoning.efforts`、`FinishReason` 断言；原先锚定「完整 Message + plugin source」的用例随源码形状更新。
- Host 半区改动不参与热重载，必须重启 Desktop 才生效。
